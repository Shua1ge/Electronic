# 工程上下文与证据驱动识别：实现复核

本方案可执行，适合现有本地4B模型和Python 3.13环境。应分开验收“事实读取”“对象消歧”“关系判定”“复查”，不能把输出JSON成功作为识别成功。本次实现为第一版基础设施与几何改进，不宣称全部本体抽取和业务推理已经完成。

## 识别流程

1. 全文OCR与页面分类；保留所有页面，说明页优先处理。
2. 从说明页保存有页码、OCR位置、文档哈希的原始陈述。新建、现状、过渡等标记仅作用于当前陈述；混合或不明确时保留未知。
3. 按当前图中的名称检索有限条相关陈述，明确提示它们可能出错。模型仍只能引用当前图的证据，不能用说明补填图中未见的字段。
4. 图形分析输出框、路径、端点标题、图例引用及不确定候选。文字读数与空间归属分别保留。
5. 工程对象候选与图纸表达分别分配ID；属性陈述附来源。身份判断输出同一对象、不同对象或证据不足，不进行名称相似度合并。
6. 生成缺端点、未绑定路径和预期数量的复查任务。复查执行器有次数与token上限，保存原始回答及下一步需要的证据，不自动覆盖业务字段。

## 关键设计修正

- 说明是待验证陈述，不是可信主数据。原文有明确的“新建两根72芯OPGW”时仅建立数量核对任务；不生成两条已确认光缆，也不按原始记录数直接宣布漏项。
- 三阶段属于对象的状态背景。阶段不同既不能直接合并，也不能直接判断为不同对象，应寻找施工活动关系。
- 10G网络、2.5G光路、2M业务分别属于不同对象属性。跨层属性不比较，不凭常用速率纠正OCR。
- 屏幕左侧不等于业务A端。模型已经明确读出反向A/Z时，不再强制按左右覆盖；无法确定方向时仍需复核。
- 图例只在同页生效。相似符号多个解释、行内标记与图例矛盾时保留待复核。图例OCR误字（如2Ni、2W）不猜成2M。
- 不把相邻双线合并成业务。连线图元、纤芯表达、业务通道分别计数。
- 所有旧模型回答和冻结评测保持原样。新的输出目录独立保存，不能复用旧准确率为新版本背书。

## 规则与案例

规则记录适用条件、支持证据、禁止条件和反例。第一版使用`project_context.RULES`保存通用规则。实际样例的正确答案留在`audit/`，识别与复查脚本均不读取它们。

案例应包含原图定位、原始OCR/模型回答、当时上下文快照、错误环节、人工判断依据、规则与反例。不能把IAD连线错配沉淀为站名替换；不能用一个项目的站名表纠正其他项目。

## 验收

程序回归覆盖：混合阶段、同两端平行线路、同名不等于同对象、上下文不得补本图速率、反向端点、多个网络标题、浅灰线、折返、交叉、歧义转折、纯短站名、图例冲突与空符号。

原图回归分别报告：检测图元数、明确路径数、未绑定数、图例唯一匹配数、业务字段命中、误改数、漏项检出与无法判定数。所有四份现有PDF均已经用于开发，后续结果只能称回归；要证明泛化必须另加未参与开发的文件。真实低清、倾斜扫描件仍需单独验证。
